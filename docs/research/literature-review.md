# CyberSeat - Critical Literature Review

Version 1.1 | October 23, 2026 | Owner: Aibekuly Alibi | [ECR-4](https://nerybr.youtrack.cloud/issue/ECR-4)

Status: documentation completed; team agreement confirmed by Alibi on October 23, 2026. This focused engineering review supports the booking module and its quality requirements. It is not a systematic review, a market study or evidence of user interviews.

## 1. Questions and selection method

The review asks: how can overlapping reservations be prevented under concurrency; how should correctness be tested; and how can access control and usability be evaluated without overstating the evidence?

Searches on October 23, 2026 used publisher/conference pages, author-hosted papers and official technical specifications. Query families included database isolation verification, concurrent application integrity, snapshot isolation, interval constraints, object-level authorisation and SUS analysis. Papers were included when they provided a method, empirical finding or explicit limitation relevant to a requirement. Vendor marketing, unsourced summaries and publications whose identity could not be verified were excluded from the source matrix. No exhaustive search count or screening flow is claimed.

The matrix contains **13 substantively used sources: 9 scientific publications and 4 technical/standards sources**. Six of nine scientific publications are from 2022-2025, within the recent five-year window. Three older papers are retained for foundational isolation and application-integrity arguments. Current specifications are used for concrete implementation behaviour; papers about older releases are not treated as descriptions of current software versions. Where a source was available only as a publisher abstract, the matrix says so and avoids unsupported detailed performance claims.

## 3. Synthesis: integrity is a business property

S01 explains the semantic gap between isolation labels and the actual anomalies an application must prevent. S03 provides an empirical reason to distrust uncoordinated application checks. For a station reservation, two individually valid reads of an empty schedule can precede conflicting inserts. The resulting design conclusion is to state an invariant over the committed records, enforce it in the database and test it through independent connections.

S02 and S11 offer different coordination mechanisms: serialisable transactions with retry, or explicit transaction-scoped locks. CyberSeat provisionally chooses a shared lock protocol plus a database overlap constraint. This reduces the amount of implicit predicate-level reasoning for the first implementation, at the cost of serialising some operations. It is an engineering choice to benchmark later, not a demonstrated superiority claim.

S10 directly supports interval representation. However, an exclusion constraint on reservations cannot, by itself, prevent a reservation from overlapping a maintenance record stored in another table. The architecture therefore requires reservation and maintenance writers to lock the same station guard before validation and write. Working-hours changes and reservations similarly coordinate through a club guard. ECR-8 must preserve this protocol when administrative endpoints are designed.

## 4. Synthesis: tests need histories and diverse conflicts

Recent work S04-S08 demonstrates several ways of checking transactional histories or generating revealing workloads. Their guarantees differ, so citing a successful weak-isolation checker would not prove that CyberSeat never double-books a station. Nor is it proportionate to implement a new general-purpose isolation checker for this diploma.

The adopted scope is domain-specific: release requests through a start barrier, preserve their input/response/operation identity, then query the committed state using an overlap oracle. Add a forced network interruption after commit, restart/reconciliation checks and booking-versus-maintenance races. A small workload that produces a comprehensible failing history is more useful here than an unsupported claim of production-scale reliability.

## 5. Synthesis: user quality and access are separate questions

S09 supports systematic calculation and interpretation of a perceived-usability measure. S13 gives concrete accessibility checks. Neither establishes demand for an esports booking service; that remains ECR-3. Prototype task observations should therefore be reported alongside questionnaire results, with participant recruitment and limitations disclosed.

S12 requires a server authorisation decision for each resource operation. UI hiding is insufficient: tests should change reservation IDs and club IDs directly. Ownership and assigned-club boundaries must remain effective even when a visitor understands the API. Reports must distinguish scheduled utilisation from actual attendance, which the proposed system cannot observe without additional evidence or hardware.

## 6. Research-to-requirement decisions and remaining gaps

| Finding | Design decision | Requirement / planned verification |
|---|---|---|
| Integrity cannot be inferred from labels or ORM validation | Database overlap constraint and common transactional write path | BR-04/09/10, NFR-01; real-DB race tests |
| Cancel/retry/network failure alters the observable history | Durable operation identity and result reconciliation | BR-06/11, NFR-03; response-loss and retry tests |
| Scheduling uses interval rather than scalar uniqueness | `[start,end)` and club-zone conversion | BR-05/14; adjacency, containment and overnight fixtures |
| Testing only one conflict pattern misses behaviours | Controlled family of cross-operation histories | NFR-01; final-state oracle after each run |
| Resource access depends on actor and object | Server owner/assignment checks | BR-07/08, NFR-02; foreign-resource negative tests |
| Perceived usability is only one quality dimension | Task metrics plus questionnaire and accessibility checks | NFR-06/07; formative prototype study |
